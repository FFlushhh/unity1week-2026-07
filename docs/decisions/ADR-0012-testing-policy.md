# ADR-0012: テスト方針を定める

## 状態

採用

## 日付

2026-07-26

## 背景

1週間開発では、すべてを自動テストする時間はありません。一方で、重要なゲームルールや
壊れやすい計算を手動確認だけにすると、変更時の不具合を見落とす可能性があります。

## 決定

テストは、費用対効果が高い箇所へ限定します。

### 自動テストを優先する対象

- Unity APIへ依存しないPure C#の計算
- スコア計算
- ダメージ計算
- 勝敗判定
- 状態遷移
- 境界値を持つルール
- バグが再発しやすい処理
- 同じ入力に対して結果が決定的な処理

### PlayModeテストを検討する対象

- GameObjectやComponentの組み合わせが重要
- PhysicsやCoroutineを含む
- SceneやPrefabの生成確認が必要
- 手動確認では再現が難しい不具合

### 手動確認を基本とする対象

- 操作感
- 見た目
- 演出
- Audio
- Inspector設定
- Scene遷移全体
- Prefab Override
- Unity Editor上の参照

## 実装方針

- テストのためだけに大規模な設計変更を行わない
- Pure C#へ自然に分離できる処理を優先してテストする
- 1つの不具合を修正した場合、再現しやすければ回帰テストを追加する
- テスト名は条件と期待結果が分かるようにする
- 複雑なMock基盤は導入しない
- カバレッジ率を目標にしない

## asmdefとの関係

Unity Test Frameworkでテストアセンブリが必要になった場合は、ADR-0006に従い、必要な範囲だけasmdefを追加します。

## 理由

短期開発の速度を維持しつつ、変更時に壊れやすいゲームルールを保護するためです。

## 代替案

### 自動テストを作らない

最速ですが、重要ロジックの変更リスクが高いため採用しません。

### 高いカバレッジ率を目標にする

1週間開発ではテスト作成が目的化するため採用しません。

## 影響

Unity Editorでしか確認できない内容は、PRの確認手順へ明記します。

PRでは、次のいずれを行ったか記載します。

- 自動テストを追加・実行した
- Play Modeで確認した
- InspectorやSceneを確認した
- 確認できなかった項目がある
