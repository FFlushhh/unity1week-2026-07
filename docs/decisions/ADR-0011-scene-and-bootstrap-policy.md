# ADR-0011: シーン構成とBootstrap方針を定める

## 状態

採用

## 日付

2026-07-27

## 背景

MVPのゲームフローが決まり、Title、Game、SNS、Resultを担当者ごとに並行実装する
必要があります。撮影画像、スコア、進行状態は画面間で引き継ぎますが、共通初期化を
担当するBootstrapシーンは現時点で必要ありません。

## 決定

- Title、SNS、Resultを別シーンにする
- Gameはステージごとに別シーンを作成できる構成とし、MVPでは1つのGameシーンだけを使用する
- MVPのGameOverはGameシーン内のUIとして表示する
- MVPではBootstrapシーンを導入しない
- シーン遷移は、遷移元シーンの担当者が実装する
- 写真、スコア、進行状態の受け渡しは、データを渡す側が実装する
- データ契約は実装前に、項目、null可否、寿命、破棄責任、失敗時の挙動を合意する
- シーンに直接機能を作り込まず、可能な範囲でPrefabとして分離する
- シーン統合とProjectSettingsの責任者はMとする

シーン担当:

| シーン | 担当 |
|---|---|
| Title | O |
| Game（MVP） | M、N |
| Game（追加ステージ） | ステージ追加時に決定 |
| SNS | 未決定 |
| Result | M、N |
| GameOver UI | O |

## Bootstrapとは

Bootstrapは、最初に起動してゲーム全体の共通処理を準備する場所です。例えば、BGM、
セーブデータ、設定、分析機能を1回だけ初期化し、`DontDestroyOnLoad`でシーンをまたいで
保持する場合に使います。各画面の前にある「共通の受付・準備係」と考えると分かりやすいです。

本ゲームのMVPには常駐が必須のサービスがなく、Title、Game、SNS、Result間で渡すデータも
写真・スコア・進行状態に限られます。そのためBootstrapは導入しません。必要になった時点で
追加できるよう、データの受け渡し契約だけは明示します。

## GameOverの構成

MVPではGameシーン内のUIを採用します。撮影タイマーを止めて失敗UIを表示するだけで済み、
写真・タイマー・入力状態の受け渡しや追加ロードが不要なためです。

| 方式 | メリット | デメリット |
|---|---|---|
| Gameシーン内UI | 実装量が少ない。タイマー停止と再試行・タイトル復帰を同じ場で扱える。MVP向き。 | Gameシーンに失敗画面のUI管理も置かれる。独立した演出を大きく作り込みにくい。 |
| 別GameOverシーン | 失敗画面のUI・演出をGameから完全に分離できる。後から画面を拡張しやすい。 | シーン遷移、状態受け渡し、ロード、戻り先の管理が増える。MVPには過剰。 |

## Bootstrap導入条件

次のいずれかが必要になった場合に検討します。

- シーンをまたいで保持するサービスや状態がある
- Audio、Save、Settingsなど共通初期化が必要
- 最初に必ず実行したい処理がある
- どのシーンからPlayしても初期化される仕組みが必要
- Addressablesなどの初期化が必要

## Bootstrapを導入しない条件

- 単一シーンで完結する
- 共通初期化が存在しない
- `DontDestroyOnLoad`を使う対象がない
- Bootstrap追加により理解とデバッグが難しくなる

## 理由

担当範囲を明確にして並行開発しやすくしつつ、現時点で不要な共通初期化基盤を
増やさないためです。

## 代替案

### 最初からBootstrap、Title、Game、Resultを分ける

共通初期化は整理できますが、現時点では初期化対象がなく、シーンとデバッグ手順が
増えるため採用しません。

### 常に単一シーンにする

画面間のデータ受け渡しは減りますが、担当者間のシーン競合が増えるため採用しません。

## 影響

- シーン間データの具体的な契約は、実装前に合意する必要がある
- Scene、Prefab、ProjectSettingsの同時編集を避ける
- Bootstrapが必要になる条件が発生した場合は、このADRを再検討する
