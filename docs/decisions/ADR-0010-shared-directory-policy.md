# ADR-0010: Sharedへ移動する基準を定める

## 状態

採用

## 日付

2026-07-26

## 背景

Vertical Slice構成では、共通処理を安易に`Shared`へ集めると、Featureの所有関係が崩れ、
Sharedが巨大な技術別フォルダになりやすくなります。

## 決定

アセットやコードを`Assets/_Project/Shared/`へ移動するには、原則として次の条件をすべて満たす必要があります。

- 2つ以上のFeatureから実際に利用されている
- 特定のFeatureに所有させるよりSharedに置く方が自然
- 共通化によって依存関係が分かりやすくなる
- Feature固有の仕様を含まない
- 共通化後のAPIまたは責務を簡潔に説明できる
- 短期開発でも保守負担が減る

次の場合はSharedへ移動しません。

- 将来再利用するかもしれない
- 似たコードが2箇所にあるだけ
- 配置先を考えるのが面倒
- Player固有だが名前だけ汎用的
- 共通化により引数、継承、設定が増える
- 1つのFeatureからしか参照されていない

## 理由

Featureの独立性を保ち、Sharedを「何でも置き場」にしないためです。

## 運用

共通化に迷う場合は、まず重複を許容します。

実際の利用例が2つ以上そろい、共通責務が明確になった段階でSharedへの移動を検討します。

Shared内でも、可能な限り用途ごとに配置します。

```text
Shared/
├── Gameplay/
├── UI/
├── Audio/
└── Utilities/
```

ただし、空ディレクトリは先に作成しません。

## 影響

一時的な重複を許容します。重複排除よりも所有関係の明確さを優先します。
