# Review Guide

## 目的

Pull Requestレビューの観点を統一し、短時間でも重大な問題を見落としにくくします。

## 最初に確認すること

- PRの目的が1つに絞られているか
- 変更理由が説明されているか
- 確認方法が書かれているか
- 関連Issueまたは仕様が明確か
- PRが大きすぎないか

## 動作

- 仕様どおりに動くか
- 既存機能を壊していないか
- 境界値や失敗時の挙動が不自然でないか
- 同じイベントが複数回発火しても問題ないか
- シーン再読み込みやゲーム再開で状態が壊れないか

## Unity

- Missing Scriptがないか
- Inspector参照が切れていないか
- Prefab Overrideが意図したものか
- Sceneに不要な変更が含まれていないか
- `.meta`ファイルが正しく含まれているか
- Tag・Layer・ProjectSettings変更が妥当か
- Consoleにエラーがないか

Unity Editorを使わずにコードだけレビューした場合は、その旨を明記してください。

## コード

- クラスの責務が理解できるか
- `public`が必要以上に増えていないか
- `SerializeField`の用途が妥当か
- `Find`系APIを安易に使っていないか
- `Update`で不要に重い処理をしていないか
- nullや参照切れが起きたとき原因を特定できるか
- 既存コードと命名・構造が一致しているか
- 不要な抽象化や汎用化がないか
- 初心者が修正できる程度の複雑さか

## アーキテクチャ

- 対象Feature内へ配置されているか
- Sharedへ早すぎる共通化をしていないか
- 他Featureの内部実装へ直接依存していないか
- 新しいManagerやSingletonが本当に必要か
- 将来機能のためだけの設計が追加されていないか

## ドキュメント

以下に変更がある場合は、関連文書が更新されているか確認します。

- ゲーム仕様
- 操作方法
- 勝敗条件
- セットアップ
- ディレクトリ構成
- 設計方針
- 使用パッケージ
- Unity設定
- 重要な技術判断

## コメントの書き方

レビューコメントは、問題点だけでなく理由と修正方向を示します。

推奨:

```text
この参照取得をUpdate内で毎フレーム実行すると不要な検索が発生します。
Inspector参照として保持するか、Awakeで一度取得する方が安全です。
```

避ける例:

```text
ここ違う
```

## 重要度

### Text Blazeバッジ

GitHubのレビューコメントでは、重要度をひと目で判別できるよう、Text Blazeに以下のスニペットを登録して使用します。

| ラベル | ショートカット |
|---|---|
| Must | `/review.must` |
| Should | `/review.should` |
| Nit | `/review.nit` |

Mustのスニペット:

```markdown
![must](https://img.shields.io/badge/review-must-red.svg) {cursor}
```

Shouldのスニペット:

```markdown
![should](https://img.shields.io/badge/review-should-yellow.svg) {cursor}
```

Nitのスニペット:

```markdown
![nit](https://img.shields.io/badge/review-nit-brightgreen.svg) {cursor}
```

Text Blazeのダッシュボードでラベル、ショートカット、スニペット内容をそれぞれ登録してください。レビューコメント欄でショートカットを入力するとバッジが展開され、`{cursor}`の位置から指摘内容を入力できます。

### Must

マージ前に修正が必要です。

- コンパイルエラー
- 参照切れ
- データ消失
- 主要仕様違反
- 明確な不具合
- mainを不安定にする変更

### Should

原則として修正しますが、期限との兼ね合いで判断できます。

- 読みにくい責務分割
- 不要な重い処理
- ドキュメント不足
- 将来すぐ問題になりそうな設計

### Nit

好みや軽微な改善です。マージを妨げません。

- 軽微な命名
- コメント表現
- 小さな整理

期限が短いため、Nitを大量に要求しないでください。

## 承認条件

- Mustが解消されている
- 対象機能の確認方法が明確
- Unity上で必要な確認が行われている
- PRの目的を満たしている
- 期限に対して妥当な品質である
